# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

SIEI = **Sistema Integrado de Entregables de Ingeniería**.

Goal: a modular web platform to manage engineering project information and to generate, control, and review deliverables ("entregables"). It must be designed to support **multiple projects**, not a single hardcoded one.

Initial domain focus is **Instrumentation & Control engineering**. Concepts likely to be part of the system (not a confirmed/final list): proyectos, equipos, instrumentos, señales, señales IO, señales de comunicaciones, RIO, racks, slots, módulos, canales, cables, lazos, documentos, entregables, revisiones.

**The data model, the modules, and the business rules are all still being discovered/defined.** Do not treat the entity list above as a finished schema, and do not treat its presence here as confirmation that any given entity, relationship, or rule is settled — it's the known domain vocabulary, not a spec. See "Working rules" below.

### Current repository state

- **`frontend/`** — Vite React+TS scaffold, still close to the template (see `src/App.tsx`). Not yet wired to anything.
- **`database/`** — **exists and is applied.** Migrations `001`–`003` under `database/migrations/`, smoke tests `001`–`017` under `database/tests/`. See "Database" below.
- **`docs/`** — the design record that produced the schema: `MODELO_CONCEPTUAL_SIEI.md`, `MODELO_LOGICO_SIEI.md`, `MODELO_FISICO_SIEI.md` (the implementation reference), `MATRIZ_COBERTURA_DATOS_SIEI.md` (field-by-field coverage of the source Excel files).
- **`reference_excel/`** — the five legacy Excel workbooks the model was reverse-engineered from. Read-only source of truth for discovery; never modify them.
- **Backend** — does **not** exist yet. Do not create it until explicitly requested.

## Planned architecture (full-stack)

- **Frontend**: React + TypeScript (under `frontend/`).
- **Backend**: Node.js + TypeScript. **Not yet created.**
- **Database**: SQL Server / Azure SQL. **Already created** — see below.

Hard constraints:
- The frontend must **never** connect directly to SQL Server. The backend is the **only** layer with database access.
- Keep frontend, backend, and database concerns separated (e.g. separate top-level packages/folders once backend and DB work begins).
- Prefer a modular, maintainable architecture — the platform is multi-project and multi-module by design, so avoid designs that assume a single project or hardcode Instrumentation & Control specifics where a general mechanism would do.
- SQL Server schema changes must go through migrations — no ad hoc/manual schema edits. Never edit an already-applied migration; add a new numbered one.
- Use stable internal identifiers (surrogate keys) for entities. Do **not** use TAG (the engineering tag/label) as a database primary key.
- **Authorization is enforced by the backend, never by the frontend** — and today, not by the database either (see "Security model").

## Working rules

- Don't invent engineering rules/business logic that haven't been confirmed by the user — this domain (I&C engineering) has real, project-specific conventions that must come from the user, not be assumed.
- When business information needed to proceed is missing, ask before assuming.
- Before significant structural changes (schema, module boundaries, cross-cutting architecture), explain the proposal and its impact before implementing.
- Never delete existing data or structures without explicit authorization.
- Document important architectural decisions as they're made (e.g. in this file or in dedicated docs — ask the user if unsure where).
- Don't implement significant features without first understanding the requirement — clarify scope/behavior with the user before building it.
- When there are multiple viable technical alternatives, present the options (with trade-offs) before picking one.

## Database

SQL Server. Schemas: **`nucleo`** (engineering data), **`cat`** (universal catalogs, no `proyecto_id`), **`seguridad`** (users, roles, project access), **`integracion`** (persistent import history — currently the P&ID/Plant 3D importer; see migration 004).

The `nucleo`/`cat` split isn't strictly "engineering vs. catalog" anymore since migration 006: deliverable-related tables (`entregable`, `revision_entregable`, etc.) live in `nucleo` because they carry `proyecto_id` and follow the same composite-FK isolation as everything else — the schema boundary is really about **carries `proyecto_id` vs. doesn't**, not "instrumentation domain vs. not".

Every migration starts with the seven `SET` options (`ANSI_NULLS`, `ANSI_PADDING`, `ANSI_WARNINGS`, `ARITHABORT`, `CONCAT_NULL_YIELDS_NULL`, `QUOTED_IDENTIFIER` **ON**, `NUMERIC_ROUNDABORT` **OFF**). These are **mandatory**, not decorative: without them every `CREATE UNIQUE INDEX ... WHERE ...` fails with error 1934, and because each index sits in its own `GO` batch the failure does not stop the script — tables and triggers get created while the filtered indexes silently do not. Any connection that later runs DML against these tables needs the same options (most drivers set them correctly; the usual offender is `ARITHABORT OFF` from legacy ODBC/OLE DB).

### Tests (`database/tests/`)

Smoke tests `001`–`027`, run manually against a dev database. They are `BEGIN TRY` / `BEGIN CATCH` blocks that `PRINT` `PASS`/`FAIL` and roll back their own fixtures. **A failure prints but does not fail the process** — they are not usable as a CI gate as written. Several depend on a project with `codigo_proyecto = 'TEST-001'` created by earlier tests, so run them in order.

### P&ID / Plant 3D import (`integracion` schema, migrations 004 and 008)

Two-phase flow (`backend/src/routes/pnidImports.ts`, `backend/src/lib/pnidImport/`): **PREVIEW** parses the uploaded report, persists a full row-by-row snapshot (`importacion_pnid_fila`, one row per physical Excel row, no exceptions) and a comparison result per row (`importacion_pnid_resultado`, which can also exist *without* a row — `fila_id NULL` — for a Plant3D-managed instrument that vanished from the new report entirely) — and never touches `nucleo.instrumento`. **APPLY** re-validates the batch is still `PREVISUALIZADO`, checks that no affected instrument changed since the preview (`instrumento_updated_at_preview` vs. current `updated_at`; any mismatch aborts the *entire* batch with `409 stale_pnid_preview`, never a partial apply), then applies each row's action inside one transaction.

Identity rule: `(proyecto_id, PnPID)` identifies the P&ID object; `TAG` can change under the same `PnPID` without creating a duplicate (`TAG_MODIFICADO`). `NO_EXISTE_EN_PNID` (an instrument's PnPID disappeared from the report) is scored only against instruments where `fuente_pnpid = 'PLANT3D'` — a manually-created instrument is never touched by this comparison. `pnpid` / `fuente_pnpid` on `nucleo.instrumento` are no longer editable through the normal instruments POST/PATCH — only this import flow (and direct DB access) can set them; a manual instrument can still exist indefinitely with `pnpid IS NULL`.

**TAG fallback for PnPID drift (`PNPID_ACTUALIZADO`, migration 008)**: found with real project data that the user's P&ID tool regenerates PnPID between exports for the same physical object while the TAG stays the same — in one real report, 67% of rows hit this. The user shared the legacy VBA macro they used before SIEI (`Actualizar_Master_Desde_IMPORT`): it searches by PnPID first, falls back to TAG if not found, and silently re-anchors the PnPID to the new value with no distinct status. SIEI adopted the same fallback (`backend/src/lib/pnidImport/compare.ts`) but keeps it auditable: when a row's PnPID matches no existing instrument but its TAG belongs to one with `fuente_pnpid = 'PLANT3D'`, it's classified `PNPID_ACTUALIZADO` (not `REQUIERE_REVISION`) and auto-applies — `applyActualizarInstrumento` re-anchors `pnpid` itself (the only case where that column is touched outside of `applyCrearInstrumento`), unlike everything else it updates, which is "content", not identity. If the TAG instead belongs to a **manually-created** instrument (`fuente_pnpid IS NULL`), the fallback does **not** apply — a P&ID report suddenly claiming a hand-made instrument still requires human confirmation, so it stays `REQUIERE_REVISION`. A defensive guard (`resolvedInstrumentoIds` in `compare.ts`) prevents two rows of the same file from both resolving to the same instrument (one by direct PnPID, one by TAG fallback) — without it, that produces a raw unique-constraint crash instead of a clean `REQUIERE_REVISION`; this can't happen through the PnPID-only path alone; it only became possible once the TAG fallback was added. `instrumento_asociado_id`/`_tag` (migration 005) has the same kind of TAG-fallback auto-resolve behavior on `instrumentoAsociadoTag` during apply, left untouched — a known, deliberately deferred, separate item, not an oversight.

The importer tolerates unknown/missing columns instead of failing: a known column absent from the file produces a warning and is excluded from comparison (never inferred as cleared); an unrecognized column is kept in the row snapshot and reported as a warning, never rejected. Header matching is case/accent/separator-insensitive (Unicode NFD-based, generalizing the legacy Excel macro's normalization).

**Real-world parsing gotcha (found via the actual reference report, `reference_excel/162281-620-Instrument List.xlsx`)**: some Plant 3D exports declare every OOXML namespace with an explicit prefix (`<x:worksheet xmlns:x=".../spreadsheetml/2006/main">` instead of the conventional unprefixed default) and reference an Excel Table object via an absolute relationship target — both are valid OOXML but exceljs's parser cannot load them. `backend/src/lib/pnidImport/parseExcel.ts`'s `normalizeNamespacedXlsx()` rewrites the specific namespaces exceljs expects unprefixed and strips the Excel Table object entirely (SIEI never reads it) before handing the buffer to exceljs. This runs unconditionally and is a no-op on normally-formed files.

### Entregables / LDI (migration 006)

First real deliverable module — first type: **LDI** (Listado de Instrumentos). Three-layer philosophy: **MASTER** (`nucleo.instrumento`, already lived) → **ENTREGABLE** (controlled document, its own numbering, `backend/src/routes/entregables.ts`) → **REVISIÓN** (frozen historical snapshot, `backend/src/routes/revisionesEntregable.ts`). A deliverable **never rereads the P&ID/Plant 3D report directly** — its only source is SIEI's own Master.

Revision lifecycle: `BORRADOR` (editable, re-previewable — `POST .../revisiones` immediately persists the full row snapshot, exactly like P&ID's PREVIEW) → `EMITIDA` | `DESCARTADA`, both final states, no transition ever leaves either. `POST .../revisiones/:id/emitir` generates the real `.xlsx` from the frozen template, stores the exact binary + SHA-256 in `revision_entregable_archivo`, and flips the state — all in one transaction. `DELETE .../revisiones/:id` on a `BORRADOR` ("descartar") is a state change to `DESCARTADA`, never a physical delete (a discarded draft still isn't real history, but the user explicitly wants the record kept). On an already-`EMITIDA`/`DESCARTADA` revision the same endpoint instead offers true physical deletion — a later, explicitly-requested exception to "both final states, no transition ever leaves either" — see "Revisiones: eliminación definitiva y fila de carátula fija" below (migration 009). Every write path re-fetches the row after `UPDATE` instead of using `OUTPUT` inline — SQL Server rejects `OUTPUT` without `INTO` on a table with an enabled trigger for that same DML type (error 334), and `revision_entregable` has one (see below).

Immutability is enforced at the DB level, not just by the backend: `TR_revision_entregable_estado_final_inmutable` (rejects any `UPDATE` once `estado` was already `EMITIDA`/`DESCARTADA`), `TR_revision_entregable_fila_estado_final_inmutable` (same, from the snapshot child table, closing the "edit the child directly" loophole), `TR_plantilla_entregable_blob_inmutable` (a template's binary is never edited in place — replacing is INSERT-new + deactivate-old, always), `TR_revision_entregable_archivo_inmutable` (an emitted file is never touched again, period). `CK_revision_entregable_emitida_completa` requires `criterios_aplicados_json`/`metadatos_snapshot_json`/`plantilla_id`/`archivo_id`/`emitida_by`/`emitida_at` all set before `estado` can become `EMITIDA`.

Two freezes beyond the row snapshot itself: `revision_entregable.plantilla_id` pins the *exact* template row used (even after it's replaced and `activo = 0`), and `metadatos_snapshot_json` freezes every carátula value (project title, AFE, VP, signatories, the up-to-5-row revision table actually written) — a historical revision never rereads `nucleo.proyecto_documentacion` to reconstruct what its own carátula said.

Ordering is configurable (`nucleo.configuracion_orden.criterios_json`, an ordered list of `{ campo, direccion }`), frozen per revision as `criterios_aplicados_json`. The `orden_instrumentos_asociados` criterion (`backend/src/lib/ldi/order.ts`) combines, in priority order: (1) the explicit `instrumento_asociado_id`/`_tag` relation when present, resolved through the **same** tag-inference function used for the fallback (so an instrument that explicitly joins another's group lands in the *same key space*, not a parallel one it can never match) (2) the legacy tag-text-inferred group (last `-`-segment, minus a trailing letter) when there's no explicit relation (3) `cat.cat_orden_tipo_instrumento` (prefix → number, seeded with the Instrumentación preset — LIT=10, HV=20, etc.) as the within-group order (4) the TAG itself as final tiebreak. Instruments with no LOCACIÓN value always sort **last**, regardless of ASC/DESC and regardless of where LOCACIÓN sits among the configured criteria — an instrument without one has no natural alphabetical place next to the ones that do, so it never leads the list just because `''` collates first.

The 20 columns actually printed for this deliverable (`backend/src/lib/ldi/columns.ts`): Ítem, N° TAG, DESCRIPCIÓN, TIPO, TECNOLOGÍA, CONEXIÓN A PROCESO, INSTRUMENTO ASOCIADO, LÍNEA, EQUIPO ASOCIADO, SERVICIO, LOCACIÓN, SISTEMA, HOJA DE DATOS, P&ID, DIAGRAMA DE LAZO, PLANO DE UBICACIÓN, MARCA/MODELO, COMENTARIOS, NODO, REV — no "N° TAG ANTERIOR" (`instrumento.tag_anterior` still lives in full on the Master; it's simply not printed or snapshotted for this entregable). INSTRUMENTO ASOCIADO (added by the user directly in the official template, column G, pushing LÍNEA/EQUIPO ASOCIADO one position right — located by header text like every other column, so this reorder needed no code change) prints `instrumento.instrumento_asociado_tag` (migration 005) as-is, the same "curated free tag, not resolved through the id" treatment already used for EQUIPO ASOCIADO; the id-based resolution in `order.ts` (used only for the `orden_instrumentos_asociados` sort criterion) is unaffected. Because `locateColumns` requires every declared column's header to exist in whatever template is active for a project, any project still using a pre-column-G template will fail LDI generation with a clear `LdiTemplateError` until that project's template is replaced through Entregables — expected, not a bug. LOCACIÓN (`instrumento.ubicacion`) is the primary **visual** grouping in the generated sheet, not just a sort key: `generateExcel.ts` inserts a synthetic section-header row before each new LOCACIÓN group (styled like the sheet's own header row — merge first, then clone `font`/`fill`/`border`/`alignment` onto only the anchor cell, see the exceljs gotcha below — merged across the full column extent detected at generation time, never a fixed range, and never itself a snapshot row or assigned an ITEM). ITEM resets to `001` (zero-padded, 3 digits) at the start of every LOCACIÓN group; this is computed at Excel-generation time from the already-persisted, globally-sequential `revision_entregable_fila.item` — no schema change needed. Row height is dynamic (`calcularAlturaFila`): never below the template's own measured base height, grows per estimated wrapped line (driven mainly by long SERVICIO values), never enlarges a row that doesn't need it.

Excel generation (`backend/src/lib/ldi/generateExcel.ts`) loads the project's stored template with **exceljs** and fills it in place. The official template is `reference_excel/Lista_instrumentos_plantilla.xlsx` (sheets **Carátula** / **Lista** — renamed by the user from "Hoja1" in a later cleanup pass, both names are recognized — header row **9**, columns A:S = the 19 official LDI fields exactly, no orphan columns) — it replaced the original `Listado_formato_Macros - PLANTILLA 1.xlsm` (LIST_INST, header row 11), which stays in the repo unused. Sheet names, header row, and every column are located by text (accent/case-insensitive), not by fixed position, so a template that renames its sheets or reorders/widens columns still works without a code change — column widths in particular are always read live from the loaded template, never hardcoded. `proyecto_documentacion.vp` is the definitive carátula VP text (e.g. "VP: Portafolio de Proyectos" for CUMBRA) — always the live DB value, never a value the template happens to show as an example. The row-count of the template's pre-formatted data block (currently 10) and the Carátula revision table's 5-row capacity (`B32:J36`, header row **37** — below the data, not above; confirmed from the template's own `LOOKUP` formula, `Lista!R3`) are hardcoded assumptions **of this specific template's geometry**, not auto-detected — a future template with different geometry would need this made configurable. Which physical row (32–36) a given revision lands on is no longer a fixed "newest = 36" rule — see `fila_caratula` in "Revisiones: eliminación definitiva y fila de carátula fija" below (migration 010).

Two exceljs limitations discovered empirically against the official template (not against the original one, which doesn't hit either): (1) it does not fully round-trip pre-existing DrawingML shapes/images — re-serializing `xl/drawings/*.xml` measurably shrinks them (17.5 KB → 7.6 KB with zero content changes) and drops `extLst`/`mc:Ignorable` vendor extensions, which makes Excel show its "we found a problem with some content" repair dialog on open even though the file still opens; (2) the template was built by copying sheets out of a much larger, unrelated legacy engineering workbook and still carries ~1470 leftover named ranges and 53 external-workbook links that exceljs cannot fully reserialize either, triggering the same repair dialog ("Removed records: Named range"). `backend/src/lib/ldi/templateSanitize.ts` fixes both, unconditionally and as a no-op on a clean file: `limpiarVinculosExternosYNombres()` strips `xl/externalLinks/*` + their relationships/Content-Types entries + the `<definedNames>` block from `xl/workbook.xml` before exceljs loads the buffer (SIEI's generator never uses a named range or external link anywhere); `restaurarDibujosOriginales()` splices the template's original, byte-identical `xl/drawings/**` and `xl/media/**` back over whatever exceljs wrote, after `writeBuffer()` — safe because the generator never adds, removes, or re-anchors a drawing, only writes cell values/styles and duplicates data rows well below where the logos/shapes live.

### Revisiones: eliminación definitiva y fila de carátula fija (migrations 009, 010)

The user generated several real test revisions on a real project and asked for two things migration 006 deliberately didn't allow: deleting an `EMITIDA`/`DESCARTADA` revision, and a carátula revision table that grows upward with each new emission instead of recomputing on every emission.

**Eliminación definitiva (migration 009).** `DELETE .../revisiones/:id` keeps its original behavior for `BORRADOR` (soft "descartar" → `DESCARTADA`, unchanged). For `EMITIDA`/`DESCARTADA` it now supports true physical deletion, gated by two things the endpoint checks itself (not just relying on the DB): the request body must carry `eliminarDefinitivamente: true` (missing it → `409 confirmacion_requerida`, so nothing is ever deleted by accident) and the caller needs the project's `administer` permission (checked in-handler, stricter than the `write` this router otherwise requires — `403` if missing). The two triggers from migration 006 that enforce final-state immutability now check `SESSION_CONTEXT(N'siei_bypass_inmutabilidad_revision')` first and `RETURN` early when it's `1`; the endpoint sets it to `1`, does the physical deletion inside one transaction, and sets it back to `0` **before** `COMMIT` — the flag never survives past its own transaction, so no other request on a pooled connection can ever inherit it. The deletion order matters because of a circular FK (`revision_entregable.archivo_id → revision_entregable_archivo.id` and `revision_entregable_archivo.revision_id → revision_entregable.id`): null `archivo_id` first, delete the archivo row, delete the fila snapshot rows, delete the revision row itself. A gotcha found while implementing this: nulling `archivo_id` on a row that's still `estado = 'EMITIDA'` violates `CK_revision_entregable_emitida_completa` (which requires `archivo_id IS NOT NULL` while `EMITIDA`) — the fix is to flip `estado` to `'BORRADOR'` in that same `UPDATE` (harmless: the whole row is deleted a few statements later in the same transaction, so nobody ever observes that transient state; the endpoint's response still reports the real `estadoAnterior`, captured before this step).

**Fila de carátula fija (migration 010).** The old design recomputed `revisionesMostradasEnCaratula` from scratch on every emission ("last 5 `EMITIDA`, newest first") and `generateExcel.ts` wrote them by array position (index 0 → row 36, 1 → row 35, …) — so a revision's row in the carátula changed retroactively every time a later revision was emitted (Rev A showed at row 36 in its own file but at row 33 in a file generated after three more emissions). The user rejected this explicitly and asked for the opposite: each revision's row is assigned **once**, the first time it's emitted, and never recalculated afterward. `nucleo.revision_entregable.fila_caratula` (`INT NULL`, `CHECK BETWEEN 32 AND 36`) persists that assignment. The algorithm (`planificarFilaCaratula` in `revisionesEntregable.ts`): the first-ever emission of an entregable gets row 36; each subsequent emission gets `min(fila already in use) - 1`; once all five rows 32–36 are occupied, the next emission evicts the occupant of the **maximum** row (the oldest still visible — `fila_caratula` set back to `NULL`, dropping off the carátula) and shifts every remaining occupant `+1` to free up row 32 for the new one. `POST .../revisiones/:id/emitir` computes the plan, writes the new revision's own `fila_caratula` in its normal `BORRADOR → EMITIDA` `UPDATE`, and — only when an eviction or a shift is actually needed — wraps the sibling rows' `fila_caratula` updates in the same `SESSION_CONTEXT` bypass described above (those rows are already `EMITIDA`, so writing to them needs the same trigger bypass as physical deletion does). Verified end-to-end with a real 6-revision sequence (A, B, C, D, 0, 1): after emitting "1", A (the oldest) is evicted (`fila_caratula = NULL`, absent from the carátula) and B/C/D/0/1 occupy rows 36/35/34/33/32 respectively — confirmed both via API assertions and by opening the generated `.xlsx` directly.

### Eliminación definitiva de instrumentos (migration 011)

The user asked to permanently delete instruments whose P&ID status is `NO_EXISTE_EN_PNID` — until now there was no hard-delete for instruments at all, only the existing soft `activo=0` deactivation. The real instruments the user wanted gone were already frozen inside an **`EMITIDA`** LDI revision's snapshot (`nucleo.revision_entregable_fila`), whose original FK (`instrumento_id BIGINT NOT NULL`, no delete action) rejected the `DELETE` outright.

The user pushed back on the premise itself, correctly: *"si ya cree un entregable ese entregable no debe estar aun amarrado a nada, yo puedo eliminarlo normal"*. Verified: `revision_entregable_fila.datos_snapshot` is already a self-contained JSON snapshot — it's the only thing `generateExcel.ts` and the revision-detail endpoint read to reproduce an emitted revision; `instrumento_id` is purely a live back-link that nothing reads once a revision is emitted. Migration 011 makes it nullable and drops the old `UNIQUE (revision_id, instrumento_id)` constraint in favor of a filtered unique index `WHERE instrumento_id IS NOT NULL` (a plain `UNIQUE` constraint in SQL Server allows only *one* `NULL` per key — with several instruments eventually deleted out of the same revision, more than one `NULL` per `revision_id` has to be possible). **No native `ON DELETE SET NULL`**: SQL Server rejects that action on a composite FK whose other member (`proyecto_id`) is `NOT NULL` (confirmed in practice, error 1761) — the backend nulls `instrumento_id` explicitly in the same transaction as the instrument's deletion instead.

`DELETE /instruments/:id` keeps its default behavior unchanged (soft `activo=0`, no body needed). With `{ eliminarDefinitivamente: true }` in the body it attempts true physical deletion, gated narrowly: the instrument's `estado_pnid_id` must resolve to exactly `NO_EXISTE_EN_PNID` (`409 instrumento_no_elegible_para_eliminacion` otherwise — this is deliberately not a generic "delete any instrument" capability) and the caller needs the project's `administer` permission (`403` otherwise, same pattern as revision hard-delete). It also rejects (`409 instrument_in_use`) if the instrument is still referenced by any `nucleo.senal` (as owner or as `instrumento_agrupador_id`), `nucleo.punto_conexion`, `nucleo.lazo`, or `nucleo.enlace_com` — those are real engineering resources, never silently cascaded. Inside the transaction: `integracion.importacion_pnid_resultado` rows with `fila_id IS NULL` (drift markers that only exist because of this instrument, per the P&ID importer's own `NO_EXISTE_EN_PNID` scoring) are deleted outright; rows with `fila_id IS NOT NULL` only get `instrumento_id` nulled (`CK_importacion_pnid_resultado_origen` requires at least one of the two to stay non-null, and those rows keep their own file-row identity); other instruments' `instrumento_asociado_id`/`_tag` pointing at this one are cleared (a curated, non-structural link, same "clean instead of block" precedent as `equipo_asociado_id` on P&ID reimport); `revision_entregable_fila.instrumento_id` is nulled for every row that referenced it. That last `UPDATE`, on a row that may belong to an already-`EMITIDA`/`DESCARTADA` revision, needs the same `SESSION_CONTEXT` bypass from migration 009 — the endpoint arms `siei_bypass_inmutabilidad_revision` before it and disarms it before `COMMIT`, identical discipline to revision hard-delete.

### Gabinetes (migration 012)

First piece of the Señales/Conexionado/Gabinetes domain to actually be implemented, after a long, purely conceptual diagnostic phase (documented in full, with real Excel/Power-Query/VBA evidence, in `docs/DIAGNOSTICO_SENALES_GABINETES.md`). The diagnostic found real project data (`620-HV-5084` and others wired into `620-PCC-5006`, a motor control cabinet) proving that `nucleo.rio` was already being used, in practice, as a stand-in for "control cabinet" more generally — not just for remote-I/O enclosures. `nucleo.rio` in the real dev database had **zero real project data** (all 28 rows were test fixtures), so generalizing it carried no real-world migration risk.

Migration 012 renames `nucleo.rio` → `nucleo.gabinete` in place (`tag_rio`→`tag_gabinete`, every constraint/index renamed to match) — same `id`, `proyecto_id`, tag value, `descripcion`, `activo`, `created_at`/`updated_at`, `created_by`/`updated_by` for every existing row, no new IDs. `cat.cat_tipo_gabinete` (RIO / CONTROL / COMUNICACION, same closed-catalog pattern as `cat.cat_tipo_equipo`) makes the concept explicit; `nucleo.gabinete.tipo_gabinete_id` is `NOT NULL` (all pre-existing rows backfilled to `RIO`, verified as fixtures beforehand — no permanent `DEFAULT`, so a new gabinete must always choose a type explicitly, deliberately stricter than `equipo.tipo_equipo_id`, which stayed optional in migration 007, because zero real gabinete data exists yet to retrofit). `nucleo.gabinete.tag_anterior` (`NVARCHAR(50) NULL`, no unique index, no FK, no identity role) mirrors `instrumento.tag_anterior` from migration 004 for the same "P&ID/WSP historical tag" concept, one layer up. `rack.rio_id`/`punto_conexion.rio_id` are renamed to `gabinete_id` (the `punto_conexion` rename required dropping `CK_punto_conexion_pertenencia_xor` first and recreating it after — SQL Server rejects renaming a column an enabled CHECK still references, error 15336); the XOR logic itself is unchanged, just `rio_id`→`gabinete_id`. `nucleo.switch.gabinete_id` (`BIGINT NULL`, composite FK to `(id, proyecto_id)` on the same project) is new and optional — a switch and a gabinete are distinct entities, this is not a rename. The three triggers that referenced `rio_id` (`TR_tramo_conexion_validar_secuencia`, `TR_senal_validar_canal_ruta`, `TR_tramo_conexion_validar_canal_ruta`) were dropped and recreated with literal bodies otherwise unchanged (diff-verified programmatically against `001_initial_schema.sql` — only the column/table renames and two error-message strings differ).

Explicitly **not** part of this migration, left for later: `caja` does **not** get a `gabinete_id` — the user rejected that relationship explicitly; a caja relates to a gabinete only through `ruta_conexion`/`tramo_conexion`/`punto_conexion`, same as any other physical node. `014_planos`, `015_terminaciones` (also scoped in the diagnostic) are deliberately not designed or implemented yet.

Backend: `backend/src/routes/rios.ts` → `backend/src/routes/gabinetes.ts` (router mounted at `/api/projects/:projectId/gabinetes` — the old `/rios` path is gone, not kept as a legacy alias, since no dependency on it was found), plus `backend/src/routes/tiposGabinete.ts` (`GET /api/catalogs/tipos-gabinete`, same pattern as `tiposEquipo.ts`). `racks.ts`/`connectionPoints.ts`/`switches.ts` all take/return `gabineteId` now; `switches.ts` additionally accepts an optional `gabineteId` on create/update. Frontend: `RiosListPage`/`RioDetailPage` → `GabinetesListPage`/`GabineteDetailPage` (routes `/gabinetes`, `/gabinetes/:gabineteId`), nav label "Gabinetes"; the gabinete form requires a `tipoGabineteId` and accepts an optional `tagAnterior`; the connection-point and route builder forms use "Gabinete" instead of "RIO" as the owner-type label.

### Señales (migration 013)

Second piece of the Señales/Conexionado/Gabinetes domain, after the same long diagnostic phase (`docs/DIAGNOSTICO_SENALES_GABINETES.md`, section 34). The reference Excel (`02_MASTER_IO_620.xlsm`) showed `tag_senal` as `NOT NULL` doesn't match real engineering: 269/269 CONTROL signals have a derivable tag, but only 46/762 (6%) COM signals do — most COM rows are raw PLC registers ("PALABRA DE ALARMAS 1", "HEARTBEAT", etc.) with no tag concept at all. Migration 013 makes `tag_senal` nullable and replaces `UX_senal_proyecto_tag` with a filtered unique index excluding `NULL`, exactly the same pattern as migration 011's `revision_entregable_fila.instrumento_id`.

`codigo_senal` (`NVARCHAR(20) NULL`) is a pure legacy/imported reference — never SIEI's identity (`senal.id` already is), never generated, never renumbered. The Excel's `ID_SENAL` (format `###-SIG-######`, union of `SENALES_CONTROL` 269 + `SENALES_COM` 762 = 1031 rows) has zero duplicates and zero overlap between the two sheets, but that evidence comes from a single dataset — the user explicitly decided **against** a `UNIQUE` constraint (a second legacy Excel with one real duplicate, not observed but not ruled out either, would otherwise block a legitimate import). A non-unique filtered index (`IX_senal_proyecto_codigo`) exists purely for lookup performance.

`causa_alarma` (`BIT NULL`) has an unusual history: the Excel column with that name is actually a **computed boolean** (`=OR(TIPO_IO="AI","DI","RTD","IN")`), not a textual description of an alarm's cause — that concept doesn't exist anywhere in the workbook. The user decided anyway to add `causa_alarma` as an **independent SIEI attribute**, deliberately decoupled from that formula, refinable later without blocking this migration. No FK, no catalog, no `tipo_io`-based `CHECK`, no derivation trigger, and — unlike `tipo_dato_com_id`/`es_loop_powered` — **no clase-based exclusivity**: it's valid on both CONTROL and COM.

`cat.cat_tipo_dato_com` (global, closed list: `BIT`/`WORD`/`DWORD`/`UINT`/`UDINT`/`DINT`/`REAL`, confirmed against `SENALES_COM.TIPO_DATO`, 716/770 populated, zero variants) backs `nucleo.senal.tipo_dato_com_id`, exclusive to COM. `es_loop_powered` (`BIT NULL`) is exclusive to CONTROL — distinct from a future, not-yet-existing `instrumento.alimentacion_instrumento` (general instrument power supply); not restricted to `tipo_io_id = 'AI'` for lack of an unambiguous rule, even though the Excel's `CONEX_TIPO = 'LP'` (the only real source for this derivation) always coincides with transmitter-style input channels. `CONEX_TIPO` also has `BOT_S`/`BOT_D` (confirmed: pushbutton-station type — simple/double — on discrete valve-command outputs, a **different concept** from loop-powered) — explicitly **out of scope**, no column, no catalog, documented as unresolved modelling debt, never interpreted as `es_loop_powered`.

Both new exclusivity rules are enforced by **extending** `TR_senal_validar_clase` (not a new trigger) — CONTROL rejects `tipo_dato_com_id`, COM rejects `es_loop_powered`, alongside its unchanged pre-existing rules (COM rejects `tipo_io_id`/`canal_id`, CONTROL rejects `direccion_com_id`, COM can't have an active route). `CK_senal_tipo_dato_com_loop_excl` is a simple row-level `CHECK` (no catalog join, same pattern as `CK_senal_tipo_io_direccion_excl`) that catches the impossible state of both columns populated at once — since `CHECK` constraints evaluate before `AFTER` triggers, it's always the one that actually fires in that case.

Backend (`backend/src/routes/signals.ts`): `tagSenal` removed from `REQUIRED_ON_CREATE` (only `claseSenalId` remains); `codigoSenal`/`causaAlarma`/`tipoDatoComId`/`esLoopPowered` added to `SIGNAL_FIELDS`, `SIGNAL_SELECT_COLUMNS`, and `serializeSignal`; PATCH's previously-hardcoded "`tagSenal` cannot be null" rejection now allows `null` (clearing the tag), matching every other optional field. `cat.cat_tipo_dato_com` is exposed at `/api/catalogs/com-data-types` reusing `createSimpleCatalogRouter` (same factory as `signal-classes`/`io-types`/`com-directions` — no bespoke router file, since the table's shape already matches). Frontend: `SignalForm.tsx` drops the TAG's `required` marker, adds a `TriStateSelect` (not a checkbox, to preserve the real `NULL`/`true`/`false` three-way state) for `esLoopPowered` (CONTROL fieldset) and `causaAlarma` (common fieldset), a `tipoDatoComId` selector (COM fieldset), and a collapsed "Avanzado" `<details>` block showing `codigoSenal` read-only, rendered only when populated. Switching `claseSenalId` now clears the fields exclusive to the class being left (`tipoIoId`/`canalId`/`esLoopPowered` when moving to COM; `direccionComId`/`tipoDatoComId` when moving to CONTROL) so a hidden stale value is never silently submitted.

### Planos (migration 014)

Third piece of the Señales/Conexionado/Gabinetes domain (`docs/DIAGNOSTICO_SENALES_GABINETES.md`, section 35). `PLANO` is the identity of an engineering drawing — deliberately separate from `ENTREGABLE`/`REVISION_ENTREGABLE` (a document SIEI generates from its own template; a plano is externally-authored CAD content SIEI only catalogs). A plano can exist with zero controlled revisions ever emitted; migration 014 doesn't create any revision/status concept for planos at all (see below).

`cat.cat_tipo_plano` (global, closed list) was seeded with `CONEXIONADO`/`INTERIOR_GABINETE`/`LAYOUT`/`UNIFILAR`, all confirmed against the reference Excel's `PLANOS` sheet (40 real rows): 33 CONEXIONADO ("DIAGRAMA(S) DE CONEXIONADO"), 5 LAYOUT (prefix `PE -`, verified 1:1 against the word "LAYOUT" appearing in the description), 2 UNIFILAR (`DIAGRAMA UNIFILAR`, a genuinely distinct electrical drawing type). `INTERIOR_GABINETE` doesn't appear as its own row in `PLANOS` — it corresponds to `PLANO_CONEX_INTERIOR`, a second plano code held constant per gabinete (never on a caja-owned row), which becomes its own `nucleo.plano` record of this type when imported. **`GANCHO` was explicitly evaluated and rejected as a type**: `SENALES_CONTROL.PLANO_GANCHO` exists only in that sheet (never in `PLANOS`), and 83% of its distinct values are literal matches of an existing `PLANOS.CODIGO` — it's a reference *from a signal* to an already-existing plano (same shape as `lazo.codigo_documento`), not a plano category; it's documented as a future signal-side reference, no column added anywhere in 014.

`nucleo.plano.codigo_plano` (`NVARCHAR(50) NULL`) is deliberately **not unique** — a real duplicate (`620-J-20039`, shared by a CONEXIONADO plano and a LAYOUT plano) was found in the only dataset available, stronger evidence than what already justified `senal.codigo_senal`'s non-uniqueness in migration 013. A non-unique filtered index (`IX_plano_proyecto_codigo`, `WHERE codigo_plano IS NOT NULL AND activo = 1`) exists for lookup only. `codigo_anterior` (`NVARCHAR(50) NULL`, same shape as `instrumento.tag_anterior`/`gabinete.tag_anterior`) is **never** populated from `PLANOS.TABLERO_WSP` — that value, confirmed with real data, is the WSP historical tag of the gabinete/caja the plano documents, not of the plano itself (same finding that already produced `gabinete.tag_anterior` in migration 012); it flows to `gabinete.tag_anterior`/a future `caja.tag_anterior` instead, never to `plano.codigo_anterior`.

`PLANOS.TABLERO` was found to mix two real entity classes — resolved 100%, zero ambiguous rows, by cross-referencing `SENALES_CONTROL.RIO` (gabinete: `620-PCC-5006`/`620-RIO-5012`/`620-RIO-5013`, 18 rows) and `SENALES_CONTROL.TAG_CAJA`/`CAJA_EQUIPO` (caja: `620-TBC-*`/`620-TBJ-*`, 12 distinct tags, 14 rows). `plano.tablero` is **not** a column — it's resolved exclusively through two real many-to-many junction tables, `nucleo.gabinete_plano` and `nucleo.caja_plano` (not a generic `plano_entidad`/`tipo_entidad`/`entidad_id` polymorphic relation), each with its own `proyecto_id` and composite FKs `(entity_id, proyecto_id)` / `(plano_id, proyecto_id)` — structurally cross-project-safe with no `CHECK` or trigger needed, same mechanism as the rest of the schema. Cardinality is confirmed N:M in both directions with real evidence, not assumed: `620-RIO-5012` has 7 planos of its own; a single LAYOUT row (`TABLERO='620-TBC-5016/5017'`) documents two cajas at once, and `620-TBC-5016` itself has 3 planos. A filtered unique index (`UX_gabinete_plano_activo`/`UX_caja_plano_activo`, on the pair, `WHERE activo = 1`) blocks only an exact duplicate *active* association, never limiting how many distinct planos/gabinetes/cajas either side can have.

Two real data-quality anomalies were found and are documented, not corrected: the `PLANO_CONEX_INTERIOR` code recorded for `620-PCC-5006` is literally the same code as an existing plano that belongs to `620-RIO-5012` (likely a copy/typo error in the legacy Excel); and the `620-J-20039` duplicate above spans two documents of different types. Migration 014 doesn't read or import `PLANOS` at all — `nucleo.plano`/`gabinete_plano`/`caja_plano` start and remain empty after applying it; a future importer's policy is planned as detect + warn, never auto-correct or auto-merge.

Backend: `backend/src/routes/planos.ts`, mounted at `/api/projects/:projectId/planos` (Spanish, following the more recent `gabinetes` precedent over the majority-English convention — "planos"/"drawings" in English don't capture the domain term as cleanly). Standard CRUD (`GET`/`GET :id`/`POST`/`PATCH`/`DELETE` soft) plus four association sub-routes (`POST`/`DELETE .../gabinetes/:gabineteId` and `.../cajas/:cajaId`) — re-associating a pair that exists but is inactive **reactivates that same row** instead of inserting a duplicate (`200` vs `201` in the response distinguishes the two). `GET`/`POST`/`PATCH` always return the full detail shape, including resolved `gabinetes[]`/`cajas[]` arrays, avoiding extra round-trips from the frontend. `cat.cat_tipo_plano` reuses `createSimpleCatalogRouter` at `/api/catalogs/tipos-plano` (same shape as `cat_tipo_dato_com`, no bespoke router). Frontend: new `Planos` module (`PlanosListPage`/`PlanoFormPage`/`PlanoDetailPage`, nav label "Planos") follows the Señales page-split pattern, not the Gabinetes inline-form pattern — creation is a dedicated page with only the plano's own 4 fields (código, descripción, tipo, código anterior); gabinete/caja associations are managed afterward from the detail page (a `CatalogSelect` + "Asociar" button per side, with "Quitar" per row) — the N:M relationships are never exposed as a multi-select inside the creation form.

### Terminaciones (migration 015)

Fourth piece of the Señales/Conexionado/Gabinetes domain (`docs/DIAGNOSTICO_SENALES_GABINETES.md`, sections 36-39 — three full rounds of design correction before implementation, the last one triggered by the user finding that `tramo_conexion.par_conductor_id` couldn't stay `NOT NULL`). First model of conexionado at the level of the *individual conductor and physical terminal*, one layer below the existing `punto_conexion`/`tramo_conexion` (which stay exactly as they were — a tramo's logical/physical endpoint — and never gain terminal-level knowledge).

**Why `par_conductor`/`punto_conexion` weren't enough**: a real cable (`620-HV-5084`, `"1-19c#14 AWG"`) has 19 individual conductors, no pairs at all — `par_conductor` (pairs only) can't represent it. And a signal like `HYO` on that same instrument needs 5 conductors landing on 5 different physical terminals at the *same* logical tramo endpoint — a single `punto_conexion.terminal_id`-style column can only ever point to one terminal, so the old draft that tried that (section 37 of the diagnostic) was explicitly discarded once this counterexample was checked.

**The 6 new tables**: `nucleo.conductor` (the physical unit of a cable — `codigo NVARCHAR(20)` because a wire is identified as `'1'`/`'BK'`/`'+'`/`'-'`, never assumed numeric; `cable_id NOT NULL`; `par_conductor_id NULL`, an optional grouping — `par_conductor` itself is untouched, no schema or data change, it just stops being "the" unit and becomes one *possible* grouping of 2 conductors, DB-enforced to share the conductor's own cable via a 3-column FK to an additive `UQ_par_conductor_id_cable_proyecto`); `nucleo.bloque_terminal` (XOR owner `caja_id`/`gabinete_id`/`modulo_id` — a module-owned block is *never* created by hand, only materialized, see below); `nucleo.terminal` (one physical borne per row — a `BORNERA` like `"F1-2"` becomes 2 rows, `numero='F1'` and `numero='F2'`, never one row holding the list; `catalogo_modulo_io_terminal_id NULL` when it came from a module's factory catalog); `nucleo.posicion_terminal` (the clamp/side within a terminal — the reason it exists: a physical terminal can legitimately hold *two* simultaneous landings, a field cable **and** an internal jumper to a module, on two different positions of the *same* terminal; occupancy is enforced at the position level, `UX_terminacion_posicion_ocupacion`, never at the terminal level); `nucleo.tramo_conductor` (declares which conductor belongs to which `tramo_conexion` — a conductor admits at most one active `tramo_conductor` anywhere, `UX_tramo_conductor_conductor_exclusivo (conductor_id) WHERE activo=1`, which is strictly stronger than and replaces the need for a `(tramo_conexion_id, conductor_id)` pair index); `nucleo.terminacion` (the physical fact itself — this conductor, in this tramo, at extremo `ORIGEN`/`DESTINO`, lands on this `posicion_terminal`; a `tramo_conductor` can validly have zero, one, or two terminaciones — unfinished engineering is a normal state, not an error).

**`cat.cat_modulo_io_terminal`**: global catalog (no `proyecto_id`, no `activo` — same rule as every `cat.*` table), 1:N per canal via `(catalogo_modulo_id, numero_canal, orden_terminal)` — *not* `(modelo, canal, etiqueta)`, because a real 3-wire RTD produces two rows with the identical label `"IN_0/A"` for the same canal; only `orden_terminal` tells them apart. A trigger, `TR_terminal_validar_catalogo_modulo`, is the DB-level guarantee that a `terminal.catalogo_modulo_io_terminal_id` can only point to a catalog row belonging to the *same* `catalogo_modulo_id` as the module the terminal's block belongs to — a terminal of one hardware model can't materialize onto a module installed with a different model.

**Materialization is automatic, mirroring `TR_modulo_generar_canales` exactly in spirit**: `TR_modulo_generar_terminales` (fires on the same `catalogo_modulo_id` INSERT/UPDATE trigger condition as canal generation) creates the module's own `bloque_terminal` + one `terminal` per catalog row + one `posicion_terminal` per terminal, all idempotent (`NOT EXISTS` guards, never a duplicate on re-run); if the module's catalog changes and a terminal that would disappear still has an occupied position, the *entire* change is rejected (error 51027) — never a silent destroy-and-regenerate. A companion procedure, `nucleo.sp_sincronizar_terminales_modulo` (exposed as `POST /modules/:id/sync-terminales`), covers the case the trigger structurally cannot: adding a *new* row to `cat.cat_modulo_io_terminal` after the module is already installed doesn't touch `nucleo.modulo` at all, so no trigger fires — the procedure re-applies the same idempotent logic on demand, for one module, without duplicating the code inside the trigger as a cross-call (deliberately duplicated logic, not shared, to keep both paths pure set-based with no cursor).

**Validation trigger `TR_terminacion_validar_propietario_y_canal`** closes two gaps at once, both DB-enforced, not just checked by the backend: (a) a `terminacion`'s `bloque_terminal` owner must be the *same* caja/gabinete/módulo as the real `punto_conexion` of that extremo of the tramo — rejects cross-owner even within the same project (error 51024); an extremo whose `punto_conexion` is instrumento/equipo is *always* rejected here too, because `bloque_terminal` has no instrumento/equipo XOR branch — bornes internos of an instrument are explicitly out of scope for 015, a conductor still exists via `tramo_conductor`, it simply has no `terminacion` on that end yet; (b) when the terminal is module-derived, its catalog `numero_canal` must equal the real `canal_id` of the ruta's señal — closes the long-standing gap where `punto_conexion.modulo_id` only ever validated against the *whole* module, never the exact canal (error 51025).

**Soft-delete discipline, both halves**: cascade down when *not* occupied (`tramo_conexion → tramo_conductor → terminacion`, `bloque_terminal → terminal → posicion_terminal` — the second pair combines "block if occupied" and "cascade if not" in the *same* trigger per table, `TR_terminal_validar_desactivacion`/`TR_bloque_terminal_validar_desactivacion`, relying on SQL Server's default nested-trigger firing to chain bloque→terminal→posición in one `UPDATE`); block outright when occupied (`conductor`, a leaf resource with no children, only ever blocks, never cascades — error 51028). `TR_cable_validar_desactivacion` is *extended*, not replaced, to recognize both the legacy path (`par_conductor → tramo_conexion.par_conductor_id`) and the new one (`conductor → tramo_conductor`) as "in use" — same error 51021 either way.

**The legacy-column evolution that makes this not-100%-additive**: `nucleo.tramo_conexion.par_conductor_id` goes `NOT NULL → NULL` (a new-model tramo has no legacy pair at all — its conductors live in `tramo_conductor` instead), and `UX_tramo_conexion_par_conductor_id` gains an `IS NOT NULL` filter (a plain SQL Server unique index otherwise treats a second `NULL` as a conflict). Exactly 2 existing triggers needed recreating (confirmed by exhaustive search — no others reference this column): `TR_tramo_conexion_validar_secuencia` (its `@activos` table variable had `par_conductor_id BIGINT NOT NULL`, which would reject *any* insert into a route touched by a null-par tramo; its cable-active check moved from `INNER` to `LEFT JOIN` on `par_conductor`/`cable` so a null-par tramo doesn't skip the point-active check it doesn't depend on) and `TR_cable_validar_desactivacion` (above). Legacy tramos with a real `par_conductor_id` keep validating exactly as before; `001`–`014` are unmodified as files — the `ALTER COLUMN` and trigger recreations live entirely inside `015_terminaciones.sql`.

Backend: `backend/src/routes/conductors.ts` (mounted at `/conductors`), `backend/src/routes/bloquesTerminal.ts` (`/bloques-terminal`, XOR caja/gabinete only — `moduloId` is explicitly rejected with a 400, never silently accepted, since those materialize on their own — nested sub-routes for `.../terminales` and `.../terminales/:id/posiciones`), `backend/src/routes/tramoConductores.ts` (`/tramo-conductores`, plus nested `.../terminaciones`). `modules.ts` gains `GET .../terminales` (read-only) and `POST .../sync-terminales`; `moduleTypes.ts` gains `GET`/`POST .../terminals` for the new catalog. `connectionRoutes.ts`'s `POST /routes` makes `segments[].parConductorId` optional (`null`/absent creates a new-model tramo) and adds `GET /routes/:id/conexionado` (read-only tramo → conductor → terminación tree — not `vw_conexionado`, which stays a documented future flat view, this is a nested JSON shape for the frontend). All the `OUTPUT INSERTED.*` statements against these 6 new tables had to go through the `DECLARE @table; ... OUTPUT ... INTO @table; SELECT * FROM @table;` pattern (never a bare `OUTPUT INSERTED.*`) — every one of them now carries at least one `AFTER INSERT` or `AFTER UPDATE` trigger, so SQL Server's error 334 (`OUTPUT` without `INTO` on a table with an enabled trigger for that DML type) fires immediately otherwise; this was caught by the API test suite, not by inspection. Frontend: a shared `BornerasSection` component (bloque/terminal/posición CRUD, tables + inline forms, no graphical editor) mounted on both `BoxDetailPage` and `GabineteDetailPage`; a read-only `ModuloTerminalesView` (with a "Sincronizar con catálogo" button) added next to the existing "Ver canales" toggle inside `GabineteDetailPage`'s module row; `RouteDetailPage` gains a read-only "Conexionado detallado" section below the existing tramos table.

Deliberately out of scope for 015 (per explicit instruction, not oversight): real import of `SENALES_CONTROL`, automatic parsing of `BORNE_JB` or the ambiguous legacy format `"F1-F2-3-4"`, puentes/jumpers as their own modeled concept (the occupancy index is additively relaxable later without a breaking change), `B_NUM_RESERVA`, CAD generation, a real `vw_conexionado`, bornes internos of instrumento/equipo, any real data load.

**Topology correction (found after the first implementation pass, before commit)**: the inherited `TR_tramo_conexion_validar_secuencia` ("Punto 6") rejected *any* intermediate node that wasn't caja-owned — including GABINETE — which blocked the approved physical rule (field cable → gabinete terminal + internal wiring → module terminal). Exhaustive search confirmed this was the *only* trigger enforcing that; `TR_senal_validar_canal_ruta`/`TR_tramo_conexion_validar_canal_ruta` only ever validated the route's final node and needed no change. Fixed inside the same `015` recreation of "Punto 6" (still not touching `001`/`012`'s files): a node strictly before the penultimate still requires CAJA; the **penultimate** node now accepts CAJA or GABINETE; and when it's GABINETE, the **final** node must be a MODULO that physically belongs to that same gabinete (`modulo → slot → rack → gabinete`, new error `51034`) — rejects GABINETE A → MODULO of GABINETE B even within the same project. A MODULO can still never be anything but the final node. `docs/DIAGNOSTICO_SENALES_GABINETES.md` section 41 has the full evidence trail, the 6 new SQL smoke cases (027, cases 28-33), the 3 new API cases, and the one pre-existing smoke test (`007_smoke_secuencia_ruta.sql`) whose "GABINETE intermediate must be rejected" assertion was updated to match the now-approved rule.

### Equipos (migration 007)

`nucleo.equipo` is a **hand-curated catalog**, not a reflection of any P&ID report — the user decides which equipment is relevant to Instrumentation's deliverables/signals, and nothing populates it automatically. Migration 007 added `plano_pnid` (a P&ID document reference, same spirit as `instrumento.plano_pnid` but with zero relation to the P&ID importer) and `tipo_equipo_id` (FK to `cat.cat_tipo_equipo`, seeded with `ELECTRICO`/`INSTRUMENTACION` — a closed list for now, chosen as a catalog specifically so equipment can later be filtered by discipline; not expanded beyond those two without a real reason). A `TAG_EQUIPO_INST`-style field (seen in a richer reference source, `02_MASTER_IO_620.xlsm` sheet `EQUIPOS` — distinguishing an equipment's own tag from the tag Instrumentation actually cares about, e.g. a VFD vs. the pump it drives) was evaluated and **explicitly rejected** by the user for this version; the official dataset (`reference_excel/equipos_620.xlsx`, 30 records) doesn't carry it and no equivalent concept was added.

`backend/scripts/seedEquiposDesdeExcel.ts` is a one-off, per-project data-loading script (not a migration, not a global catalog) — reads `equipos_620.xlsx` and POSTs each row through the real `/equipment` API (never a direct SQL insert), assigning `ELECTRICO` to every row of this dataset. Run via `npm run seed:equipos-620 -- --project <projectId>`.

**`instrumento.equipo_asociado_id` vs. `equipo_asociado_tag`**: the id is a manually-curated selection made in SIEI (via the "Equipo asociado en SIEI" selector on the instrument form); the tag is whatever text the P&ID currently says. The P&ID importer (`backend/src/routes/pnidImports.ts`) **only ever writes `equipo_asociado_tag`** — both `applyCrearInstrumento` and `applyActualizarInstrumento` used to also auto-resolve `equipo_asociado_id` by exact-tag lookup against `nucleo.equipo`, silently overwriting a manual curation on every reimport; this was found and removed. There is no trigger and no automatic matching of any kind — a manual association survives reimports unconditionally, even if the P&ID's tag now points somewhere else (a discrepancy warning is a possible future addition, not implemented). **`instrumento_asociado_id`/`_tag` (migration 005) still has the equivalent auto-resolve-on-reimport behavior** — the user asked to leave that one exactly as it is for now; it's a known, separate, documented pending item, not an oversight.

Deactivating an equipo in active use is rejected (`DELETE /equipment/:id` → `409 equipment_in_use`) when it's referenced by an active `instrumento.equipo_asociado_id` or an active `enlace_com.equipo_id` — same "resources in use cannot be deactivated" principle as canal/módulo/punto_conexion/cable, extended to equipo (it had no such guard before this migration).

### Key modelling decisions (details in `docs/MODELO_FISICO_SIEI.md`)

- **Multi-project isolation** is structural: every `nucleo` table carries `proyecto_id`, declares `UNIQUE (id, proyecto_id)`, and child FKs are **composite** `(padre_id, proyecto_id)`. Linking rows across two projects is rejected by the engine, not by convention.
- **Logical deletion**: `activo BIT` instead of `DELETE`. Uniqueness of tags and physical resources is enforced with **filtered unique indexes** (`WHERE activo = 1`), so a retired tag or a freed channel/conductor can be reused without losing history.
- **Deactivation cascades downward, never upward**: SEÑAL → RUTA_CONEXION → TRAMO_CONEXION. Reactivating a parent never restores its children — the resources they held may have been taken in the meantime.
- **Resources in use cannot be deactivated**: canal, módulo, punto_conexion and cable in active use are rejected, never silently unassigned.
- **`clase_senal_id`** (`CONTROL` / `COM`) is explicit and mandatory — the domain of a signal is never inferred from `tipo_io_id` / `canal_id` / `direccion_com_id`.
- **`updated_at`** is the backend's responsibility. The exception is automatic trigger cascades, which write it themselves because no application statement touches those rows.
- **Building a multi-segment route** (`INSTRUMENTO → CAJA → RIO`) must happen in **one statement**: validation runs after every statement, so an intermediate state ending at a CAJA is rejected. The backend must insert/update all segments of a route atomically.

## Security model

Three functional roles: **ADMIN**, **EDITOR**, **VIEWER**.

| Role | Read | Create / modify | Deactivate | Administer |
|---|---|---|---|---|
| ADMIN | ✔ | ✔ | ✔ | ✔ |
| EDITOR | ✔ | ✔ | ✘ | ✘ |
| VIEWER | ✔ | ✘ | ✘ | ✘ |

- **Roles are assigned per project** via `seguridad.usuario_proyecto_rol`. The same user can be EDITOR on one project and VIEWER or ADMIN on another. At most one active assignment per (user, project).
- **`usuario.es_admin_sistema = 1`** is a global administrator: ADMIN over every active project, without explicit assignments. It is not a fourth role. It is the highest privilege in the system and has no database-level guard — the backend must never expose it through a generic user-update endpoint.
- **`seguridad.vw_acceso_proyecto`** resolves effective access per user and project, and is the intended source for the backend's authorization checks.
- **SIEI never stores passwords.** Authentication is delegated to an external OIDC provider, initially Microsoft Entra ID. External identity is `auth_issuer` (claim `iss`) + `auth_subject` (claim `sub`), both NULL or both set; a pre-registered user who has never signed in has them NULL.
- **No RLS.** Authorization is applied by the backend. The `puede_escribir` / `puede_desactivar` / `puede_administrar` flags are **advisory metadata** — the database does not know which application user is acting, so nothing at the DB level stops an EDITOR from deactivating a record if the backend gets it wrong. This is a deliberate trade-off and contrasts with the heavy DB-level enforcement used for data integrity; the model is ready for RLS (`proyecto_id` is present everywhere) if that changes.
- **A project with `activo = 0` is ARCHIVED, not deleted.** Its access assignments are deactivated automatically, so nobody sees it through `vw_acceso_proyecto`. **Its engineering data is deliberately left untouched** — instruments, signals and routes stay `activo = 1`. There is no cascade from project deactivation into `nucleo` content.
- **`created_by` / `updated_by`** may be NULL, intentionally: migrations, bulk imports, pre-existing data and trigger-generated rows have no human author. For any change originating in an authenticated session, the backend must populate them.

## Commands

All commands run from `frontend/` (there is no root `package.json`):

```bash
cd frontend
npm install       # install dependencies
npm run dev       # start Vite dev server with HMR
npm run build     # type-check (tsc -b) then production build via Vite
npm run lint      # lint with oxlint
npm run preview   # preview the production build locally
```

There is no automated test runner for the frontend, and no backend yet. Database migrations and smoke tests are `.sql` files executed manually against SQL Server (in order: `001`, `002`, `003`, then `tests/001`–`017`) — there is no migration runner tool wired up yet.

## Current frontend implementation

- Build tool: Vite 8, using `@vitejs/plugin-react` (Babel-based Fast Refresh, not SWC).
- Language: TypeScript, project-references split into `tsconfig.app.json` (app code in `src/`, DOM lib) and `tsconfig.node.json` (`vite.config.ts`, Node lib). The root `tsconfig.json` just wires these two together via `references`.
- Entry point: `frontend/index.html` loads `src/main.tsx`, which mounts `<App />` from `src/App.tsx` into `#root` inside `React.StrictMode`.
- Linting: [oxlint](https://oxc.rs) (not ESLint), configured in `frontend/.oxlintrc.json` with the `react`, `typescript`, and `oxc` plugin sets. Type-aware lint rules are not currently enabled (would require `oxlint-tsgolint` and `"typeAware": true` in the config — see `frontend/README.md` if that's ever added).
- Static assets served as-is live in `frontend/public/` (e.g. `icons.svg`, referenced via `<use href="/icons.svg#...">`); bundled/imported assets live in `frontend/src/assets/`.
